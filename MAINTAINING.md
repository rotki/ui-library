# Maintaining @rotki/ui-library

How to land changes, release, keep dependencies current, and read CI, plus the traps that already cost
time once. [CONTRIBUTING.md](./CONTRIBUTING.md) covers conventions and verification; read it first.

**Keep this file current.** When you learn something the hard way (a tool that misleads, a bump that
breaks in a non-obvious place, a decision that should not be reopened), add it here, or to AGENTS.md if it
is a rule for code, in the same pull request. There is no other place this knowledge lives.

## Ownership

- `CODEOWNERS` assigns everything to `@rotki/frontend`.
- Access, as of 2026-11-26. Re-check after any team change. A release needs an approver of the `npm`
  environment; changing the package's npm settings (trusted publishing, owners) needs an npm owner.
  - npm package owners: `kelsos`, `lefterisjp` (`pnpm view @rotki/ui-library maintainers`).
  - Approvers of the `npm` environment, which gates every publish: `kelsos`, `LefterisJP`, `yabirgb`
    (repository settings, Environments, `npm`). Publishing itself uses npm trusted publishing (OIDC),
    configured on the package's npm settings page for `release.yml`.
  - Branch protection on `main`: one approving review, linear history, and these required checks:
    `license/cla`, `Commit lint`, `Lint & typecheck`, `Unit tests`, `E2E tests (1)`, `E2E tests (2)`,
    `Visual regression`. Admins are exempt, which is what lets a fast-forward push land a PR. Storybook
    tests and coverage are not required, so check them by eye before landing.
- Consumers: [rotki](https://github.com/rotki/rotki) (frontend, on 3.x), the premium components (on GitLab,
  built against the version rotki pins), [rotki.com](https://github.com/rotki/rotki.com) (still on 2.27.0
  as of 2026-11). A breaking change has to be carried into each of them; plan that before merging it.

## Landing pull requests

- CI must be green, including `license/cla` (it sometimes posts late on a rebased commit).
- The commit list is the changelog, so review commit subjects, not only the diff. Each commit must stand
  alone (builds, lints, passes tests).
- The history on `main` is linear and the commits are GPG-signed. GitHub's "Squash" and "Rebase and merge"
  rewrite commits and drop the signatures. To keep them, fast-forward instead:

  ```bash
  git fetch upstream main "pull/<n>/head"
  sha=$(gh pr view <n> --repo rotki/ui-library --json headRefOid --jq .headRefOid)
  git merge-base --is-ancestor upstream/main "$sha" && echo fast-forward ok
  git log --format='%G? %h %s' upstream/main.."$sha"
  git push upstream "${sha}:refs/heads/main"
  ```

  The third line must print `fast-forward ok`; if not, the PR is behind `main` (see the next point). The
  fourth lists the commits that will land; each should start with `G` (a good signature). Pushing the
  sha straight to `main` works from any checkout or worktree, with no need to check `main` out. `upstream`
  is the remote for `rotki/ui-library`; if you work in a fork, push the same sha to the fork's `main` too.

  Pushing the PR's exact commits marks the PR as merged. GitHub can lag a few seconds; confirm with
  `gh pr view <n> --repo rotki/ui-library --json state` before deleting the branch, or the PR may show as
  closed. In zsh, keep the quotes around `"${sha}:refs/heads/main"`: unquoted, `$sha:r` is read as a
  modifier and the push silently sends nothing.

- If the PR branch is behind `main`, rebase it (re-signing the commits), force-push with
  `--force-with-lease`, and wait for CI again before the fast-forward.
- Land independent PRs one at a time, rebasing the next one on the new `main`.

## Releasing

A release is three steps: bump, push the tag, approve the publish. Everything after that is automatic.

Before you start, check that CI is green on `main` and pick the bump from the commits since the last tag
(`git log --oneline vX.Y.Z..main`): a `!` or `BREAKING CHANGE:` means major, a `feat` means minor, otherwise
patch.

1. **Bump.** On an up-to-date `main`, run `pnpm run release` (bumpp). It asks for the bump, sets the same
   version in the three `package.json` files (root, `packages/ui-library`, `apps/example`), and creates the
   `chore: release vX.Y.Z` commit and the `vX.Y.Z` tag locally. It pushes nothing. The tag is signed when
   git has `tag.gpgSign` set.
2. **Push.** Push the commit to `main`, then the tag:

   ```bash
   git push upstream main
   git push upstream vX.Y.Z
   ```

   If `main` only accepts pull requests, land the release commit through a PR instead, then tag the merged
   commit yourself (`git tag -s vX.Y.Z -m vX.Y.Z <sha>`) and push the tag.

3. **Approve.** The tag starts `.github/workflows/release.yml`. Its `release` job creates the GitHub release
   with notes generated by changelogithub from the commit subjects. Its `publish` job waits for approval on
   the `npm` environment (the workflow run on GitHub, "Review deployments"), then runs `build:prod` and
   publishes to npm with provenance through OIDC. No npm token is stored anywhere.

Check that the version appears with `pnpm view @rotki/ui-library version`. The registry can lag a few
minutes behind a green publish job.

A prerelease tag (`v3.5.0-beta.1`) publishes under its identifier (`beta`), so `latest` stays on the stable
line.

Only when the release changes something for consumers (a migration step, a changed default, a visual
change) is there one more step. changelogithub leaves out commit bodies and `style:` commits, so write that
block by hand and put it above the generated list:

```bash
gh release edit vX.Y.Z --repo rotki/ui-library --notes-file notes.md
```

A major version also needs its `UPGRADING.md` section. Write it while the changes land, not at release
time.

## Dependency updates

Renovate opens the [Dependency Dashboard](https://github.com/rotki/ui-library/issues/170) and groups
updates. Work through it in passes rather than merging each Renovate PR:

- One branch per pass. One commit per bump (or per group that must move together), each with its own
  fallout fixed in the same commit, or fixes first and the bump after.
- A lint config major (`@rotki/eslint-config`) lands its rule migrations as separate commits by rule
  family, before the bump.
- Run everything: lint, typecheck, unit, storybook, `build:prod`, e2e, visual. A lockfile refresh can change
  behaviour through a transitive dependency: an axe-core bump once surfaced real a11y bugs in Storybook.
- The dashboard lags npm by about a week. Check the registry (`pnpm view <pkg> time --json`) for the newest
  version past the 7 day window.
- `minimumReleaseAge` is 7 days. `@rotki/eslint-config` and `@rotki/eslint-plugin` are exempt.
  `pnpm add --config.minimumReleaseAge=0` is not a one-off: later installs reject the lockfile. If a
  same-day version is truly needed, add a dated `minimumReleaseAgeExclude` entry and remove it later.
- After a catalog bump, auto-installed peers can keep the old version. Check with
  `grep <old-version> pnpm-lock.yaml` and fix with `pnpm update -r --depth 99 <pkg>`.
- After a toolchain bump, delete `apps/example/node_modules/.tmp` before trusting the incremental example
  typecheck.
- Reverting a bump in `pnpm-workspace.yaml` and reinstalling leaves the new version's entries in
  `pnpm-lock.yaml`. Restore the lockfile instead (`git checkout HEAD -- pnpm-lock.yaml`), then
  `pnpm install`, and check the diff holds only what you meant to change.
- Run the typecheck after every bump, even when the tests pass. A renamed option can be ignored at runtime
  without an error: msw 3 renamed `onUnhandledRequest` to `onUnhandledFrame`, and with the old name the
  unit suite stayed green while unhandled requests only warned.

### Versions held on purpose

Remove the row once it no longer applies. Last checked 2026-11-26.

| Package                         | Held at | Why                                                                                     | Bump when                                      |
| ------------------------------- | ------- | --------------------------------------------------------------------------------------- | ---------------------------------------------- |
| `vue-tsc`, `vue-component-meta` | 3.3.11  | From 3.3.12, `//` in a static template prop (a URL) corrupts the generated code         | `pnpm run typecheck` passes on the new version |
| `typescript`                    | 6.0.x   | TypeScript 7 (the Go port) waits for 7.1 stable and for Vue tooling support (see below) | 7.1 is `latest` on npm and vue-tsc runs on it  |

The vue-tsc bug was reported as vuejs/language-tools#6264, closed as a duplicate; the fix PR (#6266) was
closed unmerged. 3.3.14 still has it: `apps/example/src/views/AvatarView.vue` passes
`src="https://..."` to a `RuiAvatar` inside a `v-for`, and the typecheck reports `Cannot find name 's'`
for the loop variable. That file is the canary; rebuild `dist` and clear `apps/example/node_modules/.tmp`
before trusting a green run. `@storybook/vue3` pins `@vue/language-core` 3.3.12 for itself, which does not
affect our typecheck.

As of 2026-11-26 TypeScript `latest` is 7.0.2, and 7.1 exists only as a beta and nightlies.

**Coupled versions.** `@playwright/test` (catalog in `pnpm-workspace.yaml`) must match the Playwright
Docker image in two places: the `&playwright-image` anchor on the `storybook` job in
`.github/workflows/ci.yml` (reused by `e2e` and `visual`), and `PLAYWRIGHT_IMAGE` in
`apps/example/scripts/visual-docker.sh`. Bump all three in one commit; a mismatch breaks three CI jobs.
The image is pinned by digest: take the new digest from the registry
(`docker buildx imagetools inspect mcr.microsoft.com/playwright:vX.Y.Z-noble`, the index `Digest:` line), and
keep the tag in front of it. Then run `pnpm run test:visual` locally: a new image can change pixels.

The image's Node is Playwright's choice, not ours: from 1.65 it is Node 26, with no corepack. CI does not
care, since every job runs `setup-node` with `.nvmrc` inside the container. `visual-docker.sh` bootstraps
the `packageManager` pnpm with the image's npm and installs the `.nvmrc` Node with
`pnpm runtime set node <version> -g`, so the local run matches CI. If the script breaks after an image
bump, check that bootstrap first.

**Deferred, not held.** These need work beyond a bump and wait for their own pull request:
`tailwind-variants` 4 (a major; run the merger audit below first); `@types/node` 26 and `@tsconfig/node26`
(only with a move of `engines` and `.nvmrc` to Node 26); `chokidar` 6 (pinned to 5.0.0 by an override in
`pnpm-workspace.yaml` whose reason was never written down; find out before removing it).

**tailwind-variants and Tailwind bumps.** The `tv()` merger decides which conflicting class wins, and no
test catches a class that silently stops applying. Audit a bump: install the old and new versions side by
side in a scratch directory (`pnpm add tailwind-variants@OLD tvnew@npm:tailwind-variants@NEW`), extract
every class-list literal from `packages/ui-library/src`, run each through both with the repo's
`twMergeConfig` (`src/utils/tv.ts`), and diff. That found ten silent regressions in one earlier bump.

**TypeScript 7 trial (2026-11-09).** `typescript@7.1.0-beta` with `@vue/content-mapper@4.0.0-alpha.3` on
the library gave 2 errors, both TS2367 at `RuiFooterStepper.vue:104`, which look like a mapper bug (an event
handler on a native element inside a `v-if`/`v-else` chain over a literal union prop). `tsc-alias` skips
`.d.vue.ts` files, so `resolve:alias` would need changing before publishing that way. Start the next trial
with `RuiFooterStepper`.

## CI

`.github/workflows/ci.yml` runs on pull requests and on pushes to `main`. Jobs run in parallel, each with its
own install:

| Job           | Checks                                                                             |
| ------------- | ---------------------------------------------------------------------------------- |
| `commit-lint` | commitlint over the PR's commits                                                   |
| `validate`    | `pnpm run lint`, library typecheck (sources, specs, type tests), example typecheck |
| `unit`        | Vitest unit project with coverage (no browser, no build; generates icons only)     |
| `storybook`   | `build:prod`, Storybook build, story tests in Chromium with coverage               |
| `coverage`    | merges the unit and storybook coverage, enforces thresholds, uploads to Codecov    |
| `e2e`         | `build:prod`, example app build, Playwright in two shards with two workers each    |
| `visual`      | screenshot suite in the pinned Playwright image                                    |

Browser jobs run inside the Playwright container, so nothing installs Chromium or apt packages.
`deploy.yml` publishes Storybook to GitHub Pages on pushes to `main`. `codeql-analysis.yml` runs CodeQL.

Triage a failure from the log, not the summary: `gh run view --repo rotki/ui-library --job <id> --log`.

- An e2e failure at 0ms with `net::ERR_NETWORK_CHANGED` is the runner's network, not the code: re-run.
- An autocomplete spec that clicks right after `fill()` races the 50ms debounced search. Wait for the
  filtered option count before clicking.
- Each e2e shard runs two workers (`--workers=2`, set 2026-10-23 as an experiment). If retries or flakes
  rise, drop the flag.
- The coverage job rewrites the storybook blob's paths (`/__w/<repo>/<repo>/`) to the runner's workspace;
  blobs keep absolute paths and would not merge otherwise.
- Lint workflows with `/usr/bin/actionlint`; older builds (an old `~/go/bin/actionlint` on PATH) reject the
  YAML anchors.

## Known traps

Each of these cost real time once. They are not caught by any tool unless noted.

### Build and package

- `"sideEffects": ["**/*.css"]` means a consumer's bundler keeps a module only as far as a used export
  needs it. A bare `import './setup'` is dropped, and so is `dayjs.extend(x)` at top level next to
  `export { dayjs }` (the re-export is wired straight to the dayjs package). What works is
  `export const dayjs = withPlugins()`, a new binding whose initializer runs the setup. Unit tests never see
  this; `verify:tree-shaking` (part of `build:prod`) bundles small consumer apps and does.
- VueUse is a devDependency on purpose: it is bundled into `dist/vendor/` and tree-shaken, so consumers can
  use any VueUse version. Public types must not name VueUse types (use `src/types/dom.ts` and friends).
  `verify:dist` fails if a pnpm store path leaks into `dist/`.
- `build:prod` fails if the gzipped `style.css` grows past its budget (`verify:css-size`). Raise the budget
  only for a reason you can name in the commit.
- The example app and its typecheck read the library from `dist/`. After changing library code, rebuild
  before trusting an example typecheck error or an e2e result.
- Vite's dev server can serve a stale SFC after a rebase or two quick edits. Make a real edit to the file
  or restart.
- `pnpm install` runs the library's `prepare` script, which can run a full `build:prod` when the install is
  not considered local; expect a slow first install after switching branches.

### Vue and TypeScript

- An import named like a prop shadows the prop in the template. A component with a `readonly` prop that
  also imports `readonly` from `vue` renders `:readonly="readonly"` as the function, which is truthy. The
  typecheck does not always catch this (it missed it in the generic `RuiDateTimePicker`). Never import a
  name that is also a prop of the component.
- Vue coerces an absent boolean prop to `false`, never `undefined`, even with type-only `defineProps`. A
  check like `mobile !== undefined` is always true. Debug props in the browser through
  `el.__vueParentComponent.props` and setup state through `el.__vueParentComponent.setupState`.
- `@vue-ignore` is only honoured on an `extends` clause or intersection of a whole type, not before a single
  prop.
- Generic SFCs hoist only the leading `export` block: a local type declared before `export interface Props`
  gives TS1184 / TS4025. `InstanceType<typeof GenericSfc>` does not work; specs use
  `ReturnType<typeof createWrapper>`.
- `strictTemplates` rejects `data-*` attributes unless `dataAttributes: ['data-*']` is set in the
  `vueCompilerOptions` (it is, in each tsconfig that needs it).
- ESLint autofix can turn a merged import type-only (`computed` imported as a type), rewrite
  `/* @vue-ignore */` into a JSDoc block, or delete a comment right after `defineProps<`. Read the diff after
  `lint:fix`.
- A removed prop does not fail a consumer's typecheck; Vue passes it on as an attribute. To find them in a
  consumer, run vue-tsc with `checkUnknownProps`.

### Styling

- `tv()` `extend` and base slots do not deduplicate against variants: both classes reach the DOM and
  Tailwind's CSS order picks the winner. Never put a class in a base slot that a variant overrides.
- The `tv()` merger only knows Tailwind 4 class names. A Tailwind 3 utility (`bg-opacity-40`,
  `flex-shrink-0`) is misclassified and can drop the class it conflicts with (a slider once lost its color).
  Use v4 names.
- `p-*` is emitted before `py-*`, so a component class `py-3` beats a consumer's `py-0` on the same element.
  Default paddings on table cells live in `:where()` for that reason; keep new ones there.
- Tailwind 4 `dark:` defaults to `:where()` (no specificity); the library's dark variant uses `:is()` so it
  still beats `hover:` and `disabled:`. `translate-*`/`rotate-*` set the individual `translate`/`rotate`
  properties, not `transform`: code that checks `transform` to find a containing block must check those too.
- Quoted attribute selectors in arbitrary variants compile to invalid CSS in some consumer builds
  (lightningcss drops the rule). Select on an unquoted `data-*` attribute.
- The example app scrolls inside `body`: element screenshots need
  `html, body { height: auto; overflow: visible }` and a static header. The buttons page is route `/`, not `/buttons`. Scope page selectors to
  `getByTestId('page-content')`, or they hit the header's theme toggle.

### Tests

- happy-dom has no layout (`scrollHeight` is 0) and does not expand the `overflow` shorthand; set
  `overflowX`/`overflowY` in specs and test layout in e2e. Storybook's `userEvent.hover` does not trigger CSS
  `:hover`.
- Measure two boxes in one `page.evaluate`: images loading elsewhere shift the layout between two separate
  `boundingBox()` calls.
- `pnpm run test:visual:update <file>` does not filter: the script passes `--update-snapshots` first, so the
  file becomes its value. Call `visual-docker.sh` directly with `--update-snapshots=missing` or the file
  last.
- A green unit run says nothing about a bundle, a consumer's CSS, or real layout. Those are covered only by
  `build:prod`, e2e and visual.

### Shell

- zsh aborts a command on an unmatched glob: quote globs (`grep --include='*.ts'`). `echo ===` fails
  (`=` expansion).
